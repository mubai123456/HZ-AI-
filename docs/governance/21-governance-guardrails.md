# 治理固化规则

## 目的

本文件把 `Phase 0` 到 `Phase 4` 的治理结果固化为长期规则，避免网站在后续功能增长时重新回到“页面各写各的、配置各放各的、交互各弹各的”状态。

当前工作区仍为脏工作区。后续治理或扩展实施时，仍不得覆盖与当前任务无关的历史改动。

## 一、模板规则

- 所有页面必须先归类，再实现。允许的模板类型固定为：
  - `Dashboard`
  - `Browse`
  - `Workbench`
  - `Management List`
  - `Editor`
  - `Settings`
  - `Detail Inspection`
- 页面级主标题只允许存在于模板层，不允许壳层、页面和内容组件三处同时声明。
- 客户端内容组件若被页面模板承载，默认需要支持 `embedded` 模式，收回页面级页头。
- `WorkbenchLayout` 继续作为唯一三栏工作台骨架；不得重新扩散第二套同级骨架。

## 二、导航规则

- 用户侧导航与管理侧导航必须按分组组织，不再使用单一扁平数组直接拼接。
- 导航命名统一由 `src/lib/site-config.ts` 和 `src/lib/settings.ts` 驱动，不得再把中文名称写死在壳层或页面里。
- 改导航名称可以走配置；改导航结构必须先更新治理文档，再进入实现。

## 三、配置中心规则

- 站点品牌、工作区标签、导航命名属于 `站点设置`。
- `RunningHub / Feishu` 的非敏感基础参数属于 `集成设置`。
- `JWT Secret / API Key / App Secret / Webhook Secret` 默认属于 `仅 env` 管理。
- 密钥状态页只做状态展示与掩码透出，不做普通明文编辑。
- 新配置项接入时，必须先写清：
  - 归属
  - 默认值来源
  - 回退优先级
  - 是否需要审计

## 四、后台交互规则

- 删除类动作优先复用 `ConfirmDialog`。
- 输入型批量动作优先复用 `FormDialog`。
- 单条动作与批量动作必须分别建模，不能让单条按钮隐式依赖当前勾选集。
- 不得在 `src/components/` 中重新引入浏览器原生 `window.confirm / window.prompt`。

## 五、验证规则

- 任何“完成”“通过”“已收尾”类表述前，必须先跑新鲜验证。
- `构建通过` 至少要求一轮新的 `bun run build`。
- `配置中心正常` 至少要求一轮新的设置接口定向测试。
- `页面路径正常` 至少要求一轮真实浏览器回归，而不是只看 SSR HTML 或静态代码。
- 浏览器回归发现的控制台/网络异常，必须二选一：
  - 当轮修复
  - 记录为带证据的残余风险

## 六、响应式与可访问性规则

- 主要工作流至少需要桌面端和 `390 x 844` 移动端各验一次。
- 移动端壳层必须验证导航可打开、可关闭、不会卡住主流程。
- 模态框和抽屉必须保证焦点可进入、可关闭、可返回。
- 焦点态不能只靠浏览器默认行为碰运气，组件实现要显式保留可见焦点。

## 七、脏工作区规则

- 当前仓库默认是脏工作区，实施任何新任务前都要先确认本轮只改哪些文件。
- 不得通过回滚、重置、覆盖的方式“顺手清理”无关改动。
- 若发现与本轮目标直接冲突的他人变更，先停下并重新对齐，不硬推。

## 八、文档同步规则

- 每一轮治理或扩展结束后，都要同步更新：
  - `README.md`
  - `log.md`
  - `memory.md`
  - `tasks/todo.md`
- 治理阶段推进时，同时维护 `docs/governance/README.md` 的阶段状态和文档索引。

## 九、残余风险处理规则

- 已知风险如果不在本轮处理，必须写进正式文档，而不是只留在聊天记录里。
- 对外部数据质量问题导致的受控 `404`，允许作为非阻塞残余风险保留，但必须明确：
  - 触发条件
  - 当前影响
  - 为什么不算功能性回归
  - 后续谁来继续处理
